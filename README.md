# 会展货梯搬运工时分布

东澜会展中心 B 馆物流调度组，12 名调度和装卸领班协调 4 部货梯及外包搬运班组。。展商预约单给出装卸窗口，领班在到达排队点、上梯和交付时登记时间。调度员用电子表格合并每趟签收明细并计算均值，次展排班由 B 馆值班主管复核，班组领班接收分时段预留工时。

导入 b-hall-lift-20261119-22.csv 或同结构台账。每行一趟已完成任务，填写唯一编号、货梯编号、场馆本地开始时间、从到达排队点至交付的任务工时和其中的排队分钟。三个开始时段为 06:00–10:00 进场装货、10:00–14:00 展中补货、18:00–22:00 撤展卸货。 按装卸时段输出任务量、阈值内完成率、超限率、计划分位、尾部工时占比和超限工时中的排队占比，并提供全量合计和超限率对比图。主管据此核定下一场展会各时段的预留分钟，领班可按时段回查超限任务。

- 三个装卸时段共用一列均值，夜间长任务容易被白天的小件补货稀释。
- 调度员分别修改电子表格的筛选阈值，交接班时很难复核不同百分比是否使用同样的分钟线。
- 外包班组收到的是平均每趟工时，撤展时段偶发长任务挤占后续预约时缺少量化依据。

## 六个业务模块

1. 货梯调度总览
2. 搬运签收台账
3. 超限与分位测算
4. 装卸时段分布
5. 预留工时复核
6. 排班报告分发

## 工作剧本

1. 2026-11-24 08:30，早班调度在货梯调度总览核对 B-HL01 至 B-HL04 的四天签收台账。
2. 08:40，导入 b-hall-lift-20261119-22.csv，核对 2026-11-19 至 2026-11-22 共 120 趟，三个时段各 40 趟。
3. 08:50，选择 30 分钟固定阈值和 P90 排班分位，运行装卸工时分析。
4. 09:00，在时段明细查看进场装货有 4 趟超过 30 分钟，展中补货有 6 趟，撤展卸货有 17 趟，最长 4 趟占该时段 29.89% 工时。
5. 09:15，值班主管核对撤展 P90 计划 73 分钟及超限工时中的排队占比 40.07%，决定下场撤展的单趟预留工时及要复查的时段。
6. 09:30，导出本次时段分析，安排 16:30 定时分发给 B 馆装卸领班，供次展晚班排预约使用。

## 算法与复核

场馆本地开始时间落入左闭右开窗口。经验分布在同一个固定分钟阈值下统计按时和超限比例。计划分位按向上取整的样本秩取值，再向上取整至整分钟。按各时段最长的向上取整 10% 趟数计算尾部工时占比。每趟工时含排队。排队占比描述超限工时构成，报告仅适用于当前样本及相近排班。

空台账、任务编号重复、开始时间格式错误或落在三个窗口之外、工时超出 0.1–480 分钟、排队超出任务工时，或任一已出现的时段少于 10 趟时，停止计算并提示补录。报告显式提示没有记录的时段。 复核问题为「参照同一超限阈值和各时段尾部工时占比，下一场展会各装卸时段该按相应分位预留多少分钟？撤展时段是否需要核对超限任务的排队登记？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `task_id` | 搬运任务编号 | str |
| `elevator_id` | 货梯编号 | str |
| `started_at` | 开始时间（场馆本地 YYYY-MM-DD HH:MM） | str |
| `duration_minutes` | 任务工时（分钟） | float |
| `wait_minutes` | 排队时间（分钟） | float |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18290`
- API 文档 `http://127.0.0.1:19290/docs`
- 数据库端口 `17790`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、PostgreSQL 16 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
